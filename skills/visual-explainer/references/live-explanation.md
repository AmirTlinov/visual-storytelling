# Короткий живой опыт

Для целых групп и остатка используй готовый приём `division`. Подбери небольшой
пример под вопрос зрителя и передай его первым содержательным вызовом
`story_create` в поле `explanation`. На подготовленной установке runtime, шрифты
и рисунок уже собраны. Дополнительный код для координат, ползунков и часов не нужен.

```json
{ "model": { "kind": "division", "count": 17, "divisor": 5 } }
```

Это описание модели и её представлений. Значения выбирай по текущему вопросу;
пример в справке не является готовым ответом на любую задачу. Рисунок поддерживает
0–36 предметов и размер группы 1–12. Большие значения требуют другого представления.
Ноль предметов, неполная группа и точное деление — полноценные состояния.

Вход нормализуется в полный сохранённый документ: `version: 1`, `model.id:
"division"`, представления `groups` и `equation`. Можно явно передать свои
устойчивые ID и `views`, ссылающиеся на `model.id`. Стандартные ID представлений
получают суффикс `.view`, если совпали с ID модели. Сохранённый документ и
ответы используют окончательные ID; продолжай по ним.

`title` необязателен. Без `score` действует стандартная постановка: видны предметы,
они собираются в полные группы, затем выделяются оставшиеся и появляется равенство.
Своя короткая партитура может состоять из действий, фокуса и пауз без текста:

```json
[
  { "id": "collect", "action": "group" },
  { "id": "notice", "focus": ["remainder"], "hold": true }
]
```

Допустимые действия: `gather`, `group`, `remainder`; фокус: `groups`, `remainder`,
`equation`. Не называй остаток до группировки. `seconds` необязателен; `text`
добавляет одну короткую естественную реплику у рисунка. Формула и подписи количеств
обновляются из модели, их не дублируют в авторском тексте.

При подходящем порядке действий оставь стандартную партитуру: готовый опыт
уже имеет начало, преобразование и паузу у результата. Собственная партитура
решает конкретную содержательную задачу, а не служит обязательной обёрткой.

Для продолжения используй `story_edit` с возвращёнными `projectId`,
`sourceRevision`, новым `requestId` и `operations`:

```json
[{ "op": "set-inputs", "modelId": "division", "values": { "count": 20 } }]
```

`set-views` заменяет список представлений, `set-score` — партитуру.
Содержимое каждой операции и итоговые ссылки проверяются до публикации;
связанные представления и ссылки можно менять одним пакетом. Ошибочная
операция сохраняет принятый кадр. Явно переданный вход заменяет условие зрителя,
даже если совпадает с прежним авторским значением; остальные условия сохраняются.
Успешная запись исходника и подтверждённый показ различаются в ответе инструмента.
Для повторения запроса сохраняй его `requestId`, для новой правки бери новую ревизию.
`delivery: shown` означает наблюдённый кадр; `prepared`, `pending` и `failed`
ещё не подтверждают показ. Повтор возобновляет такую доставку без повторной записи.
Завершённый receipt остаётся историческим результатом той же операции.

Проверь существенную границу: например, при группе из пяти переход 19 → 20 → 21.
В `story_control` команда `parameters` с `values: {count: 20}` изменяет вход
зрителя; для неё нужны текущие sessionId, buildRevision и stateRevision.
Команда `cue` меняет место просмотра и не проверяет изменение количества.
Рисунок, формула и история должны сохранять выбранные зрителем условия при
перемотке. Открой реальный кадр; проверка API сама по себе не подтверждает
читаемость. Для стандартного приёма достаточно адресной проверки новой модели,
состояний и текущего кадра: принятые библиотечные тесты не повторяются на каждый вопрос.

`explanation.json` — исходник опыта. Его можно редактировать и из TypeScript:
`mountExplanation(root, document)` компилирует тот же контракт в `SceneShell` и
`Story`. Новая предметная логика использует обычные `derive` и представления
библиотеки, со своими проверками. Голос, автономный HTML, архив и видео готовятся
через действующие операции выпуска, по необходимости.
