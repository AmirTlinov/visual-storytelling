# Критический аудит авторства и качества

4 октября 2026. Проверена версия `c04b3c9`. Это оценка текущей реализации и предложение следующих изменений; перечисленные исправления ещё не внесены.

Главный источник повторной ручной работы — соединение уже подготовленных возможностей. Библиотека умеет рисовать, двигать персонажей, превращать математические объекты, проигрывать рассказ и считать физику. Однако смешанный сюжет требует отдельных правил для главы, предмета, камеры, озвучки и экспорта. Пространственные отношения часто превращаются в одноразовые координаты. Поэтому смена декораций ещё способна разрушить постановку.

Основа пригодна для дальнейшей работы. Наибольший выигрыш дадут общий контракт содержимого сцены, сохраняемые связи предметов, действия через точки взаимодействия и достоверная проверка показанного кадра. Простое расширение списка анимаций оставит эти затраты у автора.

## Охват и существующая основа

Проверены состав всех 12 публичных точек входа, зависимости 200 TypeScript-файлов `src`, каталог 42 примеров, основные владельцы исполнения, авторские CLI, проверка и доставка. Поведенческие проверки были прицельными: размещение и маршруты, дверь, смешанный рассказ, широкий и узкий кадр, доступность, ресурсы и субтитры. Полный регрессионный набор в рамках аудита не запускался.

## Подтверждённые проблемы кадра

**Разные преобразования Canvas и SVG искажают одну сцену.** Встраивание публичного `CharacterStage.mount` в контейнер 960 × 360 растягивает персонажей по горизонтали относительно фона в 1,806 раза. В исходном контейнере 960 × 650 коэффициент равен 1. Canvas заполняет обе стороны контейнера, SVG сохраняет пропорции своего `viewBox`; камера и буфер Canvas рассчитаны по размерам декорации. Владельцы: [characters.css](../src/styles/characters.css), строки 7–13, [stage.ts](../src/characters/stage.ts), строки 157–195. Нужна одна геометрия видимой области для всех слоёв, включая общие правила вписывания и координаты ввода.

**Обычный `review DIST` не получает сведения об обрезке.** [open-scene.mjs](../tools/open-scene.mjs), строки 104–109, читает только `data-layout-error`. `presentation()` здесь не вызывается. Узкое воспроизведение: владелец сообщает об обрезанном персонаже, адаптер возвращает `diagnostics: []`, число вызовов `presentation` равно нулю. В [scene-capture.mjs](../tools/motion/scene-capture.mjs) эти данные становятся отчётом. Живая запись браузера уже умеет получать `content-clipped`; нужно подключить существующего владельца к обоим путям.

**Успешное вписывание ещё не проверяет читаемость.** На поверхности 375 × 760 математическая глава `story-workshop` в момент 45 с помещается в рамку 335 × 223,3. `presentation()` возвращает пустой `clipped` и ноль непроверенных Canvas. Подписи из [scene.js](../examples/story-workshop/scene.js), строки 82–94, при этом становятся примерно 9,3–10,8 CSS px. [scene-frame.ts](../src/scene-frame.ts) проверяет прямоугольники, но не минимальный экранный размер текста, перекрытие важных деталей и содержательность кадра. Требуется адаптация композиции и ракурса; масштаб клетки должен оставаться общим с рисунком.

**Перенос главы в Canvas теряет подробности диагностики.** [Storybook](../src/book/storybook.ts), строка 69, регистрирует границы целой главы. Внутренние персонажи и предметы не передаются как отдельные инспектируемые объекты страницы. У обычного [CharacterStage](../src/characters/stage.ts) другая граница: SVG props получают `data-review-id` и проверяются через DOM, но отсутствуют в `bounds` камеры, строки 140–157. Их нельзя выбрать через `shot.focus`. Нужен общий перечень смысловых предметов с границами, видимостью и намеренным выходом за кадр, сохраняемый при композиции представлений; неполная проверка должна оставаться явно неполной.

**Скрытое 3D-тело оставляет текст в дереве доступности.** В `volume-morph` после `morph.object.visible = false`, `morph.render(0)` и обновления view подпись «1» остаётся доступной для скринридера. Речь о текстовом эквиваленте, скрытом от зрячего зрителя. [body-3d.ts](../src/morph/body-3d.ts), строки 14–17 и 56–59, не синхронизирует видимость с родителями; [viewport/labels.ts](../src/viewport/labels.ts), строки 26–31, уже учитывает её для другого вида подписей. Нужна согласованная видимость представления и текстового эквивалента.

## Где постановка теряет универсальность

**Связь «книга на столе» сохраняется только до следующей перестановки.** [arrange](../src/characters/staging/layout.ts) вычисляет отношения и возвращает координаты без исходных зависимостей. Воспроизведение:

```js
const first = arrange(readingRoom(), {
  objects: { book: { at: { of: 'sideTable', side: 'on' } } },
});
const moved = arrange(first, {
  objects: { sideTable: { at: { x: -3, z: 2 } } },
});
```

Стол оказывается в `(-3, 2)`, книга остаётся в `(2.8, 1.9)` на прежней высоте. Это ограничение последовательных вариантов `arrange`: обещания живой привязки у текущего API нет. Для удобной смены декораций нужен сохраняемый граф авторских отношений; координаты должны быть его производным результатом. Именованные места подхода также должны следовать за своими опорами.

**Маршрут учитывает мебель, но не встречное движение и наличие опоры.** В одном двухсекундном эпизоде два героя идут из `(-2, 1)` и `(2, 1)` навстречу друг другу. На первой секунде оба оказываются в `(0, 1)`. Обычная `walk` также принимает маршрут с высоты 2,24 до 0 без лестницы: промежуточная высота 1,12. [navigation.ts](../src/characters/staging/navigation.ts) строит обход статических прямоугольников; [blocking.ts](../src/characters/staging/blocking.ts) не задаёт связность этажей и занятость пути во времени. Нужны поверхности опоры, переходы между ними и согласование маршрутов участников.

**Закрытую дверь нельзя открыть изнутри.** `routines.leave` сначала выполняет проход и получает `Open door ... before passing through it`. Добавленный `openDoor` получает `Operate the door from its outside handle`: [blocking.ts](../src/characters/staging/blocking.ts), строки 243 и 263. Модель двери должна предоставлять ручки и подход с обеих сторон, порог, направление открытия и свободное место для створки. Последовательность должна учитывать начальное состояние двери.

**Глаголы зависят от конкретных видов мебели.** В [types.ts](../src/characters/staging/types.ts) 21 действие и 9 видов предметов, однако `take` берёт только книгу, `put` кладёт её только на стол, одна скамейка считается одним местом. `point` и `press` получают координату без контракта состояния целевого устройства. Книга занимает руки целиком, совместные действия с ней запрещены. На персонажа разрешено одно `perform` в эпизоде. Эти ограничения находятся в [blocking.ts](../src/characters/staging/blocking.ts), строки 137–217, 306–309 и 369–374.

Здесь нужен договор между действием и предметом: точки захвата, опоры, места для сидения, ручки, поверхности для рисунка, доступные эффекты. Тогда чашка, письмо и прибор используют подготовленное действие взятия. Действия должны объявлять занятые части тела и длительность фаз: подход, контакт, действие, отпускание. Выражение лица и взгляд смогут сопровождать ходьбу и работу свободной руки.

**Хореография ещё привязана к долям демонстрационного эпизода.** В [motion.ts](../src/characters/staging/motion.ts) на подход выделено 24–30% независимо от расстояния; разворот мгновенно меняет `facing` на середине эпизода, строка 78. [routines.ts](../src/characters/routines.ts) содержит пять полезных последовательностей с фиксированными секундами и текстом. Для переноса на другой сюжет нужны скорость и естественная длительность действия, выразительные переходы между позами, точки синхронизации с речью. Стилевые параметры движения должны быть отделены от геометрии контакта.

## Чего не хватает автору смешанной истории

**Единое содержимое главы.** [StorybookOptions](../src/book/storybook.ts) принимает только `BookPage | CastChapter`. Внешние SVG props явно запрещены, строки 22–25. [BookStoryOptions](../src/book/story.ts), строки 8–13, не принимает audio или внешний Script. Общий `Story` уже есть, однако подключение книги создаёт отдельный авторский контракт. Персонаж, Ink/Math, схема, Explorer и записанная симуляция должны составляться через небольшой общий интерфейс представления главы. Книга остаётся оформлением вступления и перехода. Время, параметры и плеер сохраняют нынешних владельцев.

**Связь речи и действия при правках.** `CharacterStory` уже принимает audio и Script с готовыми метками. Автору всё ещё нужно согласовать `beats`, `narration.json` и cue IDs. Нужна подготовка этих результатов из одного авторского сценария, в котором реплика и видимое действие остаются отдельными полями. После изменения реплики кэш озвучки и компилятор постановки должны совместно пересчитывать длительности, паузы и точки контакта. Синхронизация рта и разговорных жестов — следующий потребитель той же дорожки речи; сейчас в API персонажей её нет.

**Содержимое предметных поверхностей.** Сейчас `board` — подготовленная геометрия без слота содержимого, а [PaperPage](../src/book/paper.ts) предлагает отдельные Canvas-примитивы. Вставить существующую формулу, график или SVG-объяснение на доску с правильной перспективой, глубиной, клипом, выбором и камерой нельзя одним общим способом. Следует развить нынешние Surface/Ink и адаптеры Viewport3D: локальные единицы, преобразование в сцену, границы и интерактивное содержимое. Рисунком продолжает владеть его существующее представление. Один рисунок сможет жить на листе, доске, экране прибора и в крупном плане.

**Композиции объяснения поверх существующих примитивов.** Рецепты чисел, матриц, формул, графиков и переноса уже есть. Следующий полезный уровень — сравнение, разбиение целого, цепочка причин, поток данных, дерево, временная шкала и переход «предмет → схема → формула». Такие композиции должны размещать объекты и подписи, сохранять идентичность между шагами и выбирать разумный фокус. Предметная модель остаётся обычным кодом сцены; отдельный язык описания всей науки не требуется.

**Постановка внимания.** `shot.focus` в подготовленной сцене выбирает целого героя или зарегистрированный предмет. Для объяснения часто нужны лицо, руки с книгой, порог или конкретная формула. Требуются именованные детали, кадры действия и реакции, предсказуемые переходы ракурса, сохранение направления движения и места предмета между планами. Страх и отчаяние должны сочетать позу, взгляд, темп, реакцию на причину и действие; одного клипа выражения лица для этого недостаточно.

**Наборы облика и окружения.** Сейчас встроены четыре облика и два варианта одежды одной Chibi-семьи; `characters new` начинает от Tesla или Mira. SVG-исходники компилируются в растровый атлас для Spine. Следующее расширение — совместимые детали лица, волос, одежды и аксессуаров, размеры и точки крепления; комнаты и улицы из модулей с теми же опорами и проекцией. Визуальные варианты должны проходить проверку тех же контактов и ракурсов. Автоматическая сборка атласа уже решена; автор всё ещё рисует недостающую деталь.

**Общий replay симуляции.** `physical-objects` уже можно экспортировать: пример вручную добавляет `restore(initial) → step(time × 120)` и методы `root.scene`. Почти такой же код повторён в [index.ts](../examples/physical-objects/index.ts), строка 49, и [three.ts](../examples/physical-objects/three.ts), строка 56. Нужен небольшой общий адаптер записи, перемотки и checkpoints, использующий текущую модель и `PhysicsPlayer`. Возможности живого и записанного опыта должны быть явными.

**Авторский комплект для агента.** CLI умеет искать примеры, создавать проект и показывать API. Однако каталог, навык и примеры находятся только в авторском checkout, что честно описано в README. Устанавливаемому комплекту нужны согласованные версии инструкций, каталога, шаблонов и runtime; сведения о показанной ревизии, предметах и возможностях сцены. Основная часть этого направления уже спроектирована в [Codex Plugin TDD](codex-plugin-tdd.md). Документ помечен как проект решения; соответствующий plugin/session-контракт ещё не реализован. Его следует развивать вместе с владельцами библиотеки.

## Легаси и повторяемый ручной код

На уровне файлов подтверждённого мёртвого production-кода не найдено: все исполняемые TypeScript-модули достижимы от публичных экспортов. Ambient `assets.d.ts` закономерно находится вне графа импорта. Достижимость не доказывает полезность каждой ветки. `noUnusedLocals` и `noUnusedParameters` уже включены. Удаление всей ветки только из-за отсутствия её в одном примере было бы необоснованным.

Следующие участки продолжают работать и требуют оценки повторяемого ручного кода или унификации:

## Порядок доработки

Каждый пункт должен закончиться работающим пользовательским сценарием и удалением вытесненного кода. Новые каталоги без проходящего через них рассказа не уменьшают ручную работу.

1. **Достоверный показ и выпуск существующей сцены.** Соединить геометрию слоёв, presentation и review; исправить видимость подписей, ресурсы, captions и поставку типов. Один текущий рассказ проходит широкий и узкий контейнер, обзор кадра и выпуск HTML/MP4/SRT/source. Обрезка и непроверенное содержимое видны в отчёте. Размеры и читаемость подтверждаются реальным кадром.
2. **Озвученный рассказ из разных представлений.** Через нынешний Story собрать персонажа у доски → математическое превращение → управляемый опыт → возвращение к герою. Книга используется на вступлении и переходе. Общие cue IDs, параметры, речь, исследование и обратная перемотка; внутри главы сохраняются доступные предметы. Действующие обёртки становятся тонкими адаптерами этого пути.
3. **Переставляемая комната с полноценными взаимодействиями.** Сохранить отношения предметов; добавить опоры, порталы и слоты взаимодействия. Герой открывает дверь с обеих сторон, берёт разные предметы, садится, читает и возвращает предмет. Второй герой проходит навстречу без совмещения тел. Смена расположения мебели, роста и одежды сохраняет контакты без ручных координат суставов.
4. **Повторное использование объяснения и постановки внимания.** Реализовать несколько наиболее полезных композиций и предметных поверхностей. Одна схема работает отдельно, на доске и на странице. Камера умеет показать руку с предметом и перейти к его содержимому; текст остаётся читаемым на 375 px и широком экране. Сетка и геометрия используют одинаковые единицы во всех состояниях.
5. **Расширяемая визуальная семья.** Добавить совместимые детали персонажей, предметов и декораций с метаданными контактов. Начать с нескольких существенно разных силуэтов и окружений, проверяемых одной постановкой. Подготовить жесты разговора, ожидание, реакцию, страх и отчаяние как сочетаемые выразительные действия. Сохранять принятый визуал Tesla и общий характер рисунка.
6. **Замкнутый рабочий цикл агента.** Развить уже описанный plugin/session-контракт: найти основу → изменить предметные данные → автоматически собрать → получить показанную ревизию и диагностику → исследовать → выпустить. Инструкции, каталог и API должны соответствовать закреплённой версии проекта. Использовать текущие сборщик, кэш речи, Story и SceneHandle.

Проверка достаточности — три новых рассказа разных типов: исторический эпизод, математическое объяснение и устройство или алгоритм. Для каждого фиксировать, что автору пришлось дописать вручную: координаты, фазы, привязки, адаптеры, настройку камеры и выпуск. Следующую общую возможность выбирать по повторяющейся работе в этих рассказах. Скорость пока не измерена; обещать коэффициент ускорения по числу готовых действий преждевременно.

Целевой результат: автор меняет смысл, текст, персонажей и окружение; библиотека сохраняет контакты, временные связи, масштаб, читаемость и выпуск. Новая предметная иллюстрация может потребовать рисунка или модели. Для неё уже должны существовать удобные места подключения, общие действия и проверка результата.
